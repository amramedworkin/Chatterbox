Chatterbox System Specification
1. System Overview

The primary objective of the Chatterbox system is to function as a backend application that processes user queries submitted via email or SMS/MMS, interacts with a Large Language Model (LLM) to generate a response, and returns that response to the user.

1.A. Input Channels: The system will accept incoming messages from two primary channels:
1.A.1. A designated Gmail account, the address of which will be configurable.
1.A.2. A designated phone number for receiving SMS and MMS messages.

1.B. Query Processing: Upon receipt, each message will be transformed into a standardized format suitable for querying an LLM.

1.C. LLM Integration:
1.C.1. The initial implementation will integrate with OpenAI's models.
1.C.2. Future versions will be designed to accommodate additional LLM providers, such as those available through AWS Bedrock.

1.D. Response Formatting and Delivery: The response generated by the LLM will be formatted for readability and sent back to the user's originating email address or phone number.

1.E. Message Persistence: The system will offer a configurable option for users to store their message and response history for future retrieval.

2. User Account Management

2.A. Account Requirement: To utilize the service, users will be required to create a Chatterbox account.

2.B. Pre-Registration Access (Grace Period):
2.B.1. Initially, the system will operate in an "open" mode, allowing queries from any email address or phone number to be processed without a registered account.
2.B.2. A mechanism will be implemented to disable this open access mode once the user registration and account management features are fully deployed.

3. Usage Tracking and Limits

3.A. Usage Metrics: For each interaction with the system, the following metrics will be recorded:
3.A.1. A counter will be incremented for every query received.
3.A.2. A separate counter will be incremented only upon the successful completion of a query, defined as the LLM returning a response that is then successfully forwarded to the user.

3.B. Free Usage Tier: These metrics will enable the system to enforce a limit on the number of free queries a user can make before being required to register for a paid account.

4. Account and Subscription Types

4.A. Pay-Per-Use: The user's payment method is charged for each individual query.

4.B. Prepaid: The user purchases a block of credits, which are then debited for each query.

4.C. Subscription Tiers:
4.C.1. Daily:
4.C.1.a. Allows for unlimited usage within a 24-hour period, subject to a fair-use limit to prevent abuse.
4.C.1.b. Available as a one-time purchase or a recurring subscription.
4.C.1.c. Recurring daily subscribers will receive one free day of service after every seven consecutive paid days.
4.C.2. Weekly:
4.C.2.a. Allows for unlimited usage within a 7-day period, subject to a fair-use limit.
4.C.2.b. Available as a one-time purchase or a recurring subscription.
4.C.2.c. Recurring weekly subscribers will receive five free days of service after six consecutive months of subscription.
4.C.3. Monthly:
4.C.3.a. Allows for unlimited usage within a 30-day period, subject to a fair-use limit.
4.C.3.b. Available as a one-time purchase or a recurring subscription.
4.C.4. Annual:
4.C.4.a. Allows for unlimited usage within a 365-day period, subject to a fair-use limit.
4.C.4.b. Available as a one-time purchase or a recurring subscription.
4.C.4.c. After the first year, recurring annual subscribers will receive one free month of service for each year of their membership.

5. Data Persistence and Query Records

5.A. Query Record: For each query processed, a permanent record will be created containing the following information:
5.A.1. The user's originating email address or phone number.
5.A.2. The size of the query in both bytes and tokens.
5.A.3. An indicator of whether the query was a standalone request or part of an ongoing conversation.
5.A.4. The size of the LLM's response in both bytes and tokens.
5.A.5. Timestamps for when the query was received, processed, and when the response was sent back to the user.
5.A.6. The specific AI model used for the query, and whether this model was the user's preferred choice or the system's default.
5.A.7. A detailed cost breakdown for the query, including:
5.A.7.a. The cost charged by the LLM provider.
5.A.7.b. A portion of the system's infrastructure and maintenance costs.
5.A.7.c. Any other ancillary costs, such as software licensing fees.

6. Query Types and Features

6.A. Query Structure: Queries can be either standalone, single-turn questions or part of a multi-turn conversation.

6.B. File Attachments:
6.B.1. Users can include file attachments with their queries, subject to the file types supported by the selected LLM.
6.B.2. Files attached to a user's email or sent via MMS will be automatically included in the request sent to the LLM.
6.B.3. If the LLM rejects a file due to an unsupported format, the query will still be processed, and the user will be notified of the file rejection in the response.

6.C. Standalone Queries: These are single prompts sent to the LLM without any prior context.

6.D. Conversational Queries:
6.D.1. These queries are part of an ongoing dialogue with the LLM.
6.D.2. Conversations are maintained on a per-model basis; a conversation cannot be continued with a different model.
6.D.3. Not all LLM models may support conversational context.
6.D.4. Each turn in a conversation is identified by a unique GUID (Globally Unique Identifier) to maintain context.
6.D.5. The conversation feature is only available to users who have enabled message persistence in their account settings.

6.E. Retrieval of Persisted Queries: Users can retrieve their past queries and responses at a significantly reduced cost compared to executing a new query.

7. User Profile Settings

7.A. Subscription Management: Users can select and manage their subscription plan (Pay-Per-Use, Prepaid, Daily, Weekly, Monthly, Annual).

7.B. User Information: The profile will store the user's name, email address, and username.

7.C. Payment Information: The system will securely store the user's credit card or other payment information.

7.D. Persistence Setting: A toggle to enable or disable the storage of query history.

7.E. Budget Controls (for Pay-Per-Use):
7.E.1. Users can set spending limits for various timeframes:
7.E.1.a. Maximum cost per query.
7.E.1.b. Maximum daily, weekly, monthly, and annual spending.
7.E.2. The system will provide multiple notification warnings as the user's spending approaches these predefined limits.

7.F. LLM Preferences:
7.F.1. Users can select their preferred LLM provider and model.
7.F.2. An option will be available to automatically use the most recent model offered by a provider.
7.F.3. The system will clearly indicate the current default model, and users will be informed of any discounts applied for using this model.

8. Communication Protocols

8.A. Email-Based Queries:
8.A.1. To initiate a query via email, the user must include the word "chatterbox" in the subject line.
8.A.2. Conversational Emails:
8.A.2.a. To continue a conversation, the user can place the conversation's GUID, formatted as <<<guid>>>, anywhere in the subject or body of the email.
8.A.2.b. If the user's profile has persistence enabled, the system will retrieve the corresponding conversation history and append the new query.
8.A.2.c. If no conversation matching the provided GUID is found, the GUID will be ignored, and the query will be treated as a standalone request.
8.A.3. Model Selection in Emails:
8.A.3.a. The user can specify a particular LLM model by including its name, formatted as <<<model_name>>>, anywhere in the subject or body.
8.A.3.b. The system will attempt to use the specified model if it is supported.
8.A.3.c. If the specified model is not supported, the system will revert to the user's default model.
8.A.4. Query Content from Emails:
8.A.4.a. The body of the email will be used as the primary content for the query.
8.A.4.b. If the email has no body, the subject line (with "chatterbox" and any GUIDs or model names removed) will be used as the query.
8.A.4.c. If both the body and a valid subject line are absent, the query will be rejected.
8.A.5. Rejection Notifications for Emails:
8.A.5.a. An email notification will be sent to the user upon query rejection.
8.A.5.b. To prevent spam and denial-of-service attacks, these rejection notifications will be rate-limited to one per five minutes for any given user. This time limit will be a configurable system parameter.

8.B. SMS/MMS-Based Queries:
8.B.1. Implicit Queries: All messages sent to the designated Chatterbox phone number will be treated as queries; the keyword "chatterbox" is not required.
8.B.2. Account Requirement: There will be no free usage tier for SMS/MMS queries. A user must have a registered and funded account to use this feature.
8.B.3. Conversational SMS/MMS:
8.B.3.a. To continue a conversation, the user must begin their message with the conversation's GUID, followed by a space. For example: f81d4fae-7dec-11d0-a765-00a0c91e6bf6 What is the weather like today?
8.B.3.b. If the user's profile has persistence enabled, the system will retrieve the conversation history.
8.B.3.c. If no conversation matching the GUID is found, the GUID will be ignored, and the message will be treated as a new, standalone query.
8.B.4. Model Selection in SMS/MMS:
8.B.4.a. The user can specify an LLM model by including its name, formatted as <<<model_name>>>, anywhere in the message.
8.B.4.b. The system will use the specified model if supported; otherwise, it will revert to the user's default model.
8.B.5. Query Content from SMS/MMS:
8.B.5.a. The text content of the SMS or MMS message (with any GUIDs or model names removed) will be used as the query.
8.B.5.b. Any media content (images, videos) included in an MMS message will be treated as a file attachment and sent to the LLM.
8.B.5.c. If the LLM cannot process the MMS content, it will be ignored, but the text portion of the query will still be executed.
8.B.6. Handling of Empty or Invalid Messages:
8.B.6.a. Empty or blank messages will be rejected.
8.B.6.b. A nominal fee (e.g., $0.01) will be charged for each rejected empty message to discourage spamming.
8.B.6.c. Rejection notifications for empty messages will be rate-limited to prevent abuse.

8.C. Response GUIDs:
8.C.1. Every response sent by the system, whether via email or SMS/MMS, will include a GUID.
8.C.2. If message persistence is enabled, this GUID serves as the unique identifier for the conversation, allowing the user to continue the dialogue.
8.C.3. For all queries, the GUID also serves as a reference for billing and support, linking the response back to the specific query record and its associated costs.
